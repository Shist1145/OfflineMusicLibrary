# 数据安全、扫描与状态恢复

本说明适用于 Windows 完整版 1.6.3 及 1.7.0-preview.1。目标是：移动硬盘临时离线、扫描被取消、应用双开、保存中断、超大/损坏输入或单个 JSON 损坏时，不把一次异常扩大为整个曲库和歌单丢失。

## 状态文件

默认目录：

```text
%LOCALAPPDATA%\OfflineMusicLibrary
```

主要文件：

| 文件 | 作用 |
| --- | --- |
| `library-v2.json` | 最新完整落盘的状态 |
| `library-v2.backup.json` | 上一次保存前的有效主状态 |
| `library-v2.previous.json` | 再上一代有效备份 |
| `library-v2.write.lock` | 防止多个保存方同时替换状态文件 |
| `library-v2.*.tmp` | 同目录临时写入；正常保存结束后删除，超过一小时的遗留文件会在下次启动时清理 |
| `library-v2.invalid-*.json` | 启动时发现损坏主文件后保留的诊断副本 |

状态包含文件路径、标签缓存、歌单、收藏、播放次数和设置，不包含媒体文件本体。

### 1.7.0-preview.1 的兼容扩展

1.7.0 NAS Foundation 源码把状态内部格式升级为 v3，但继续使用上述 `library-v2*.json` 文件名，避免为了新增字段搬动或覆盖整套恢复文件：

- 原 `LibraryFolders` 会迁移为带稳定 ID、类型、健康、最近在线、延迟和错误的根目录状态，同时保留兼容路径列表。
- 原 `LastTrackId` 与 `LastPlaybackPositionMs` 会迁移为完整播放会话；旧字段继续更新，便于回退和诊断。
- 队列、当前索引、循环/随机模式、最近随机历史和等待中的 NAS 根目录进入同一套临时落盘、文件锁、原子替换与三代恢复流程。

封面和歌词缓存单独放在 `%LOCALAPPDATA%\OfflineMusicLibrary\asset-cache`，不塞进曲库 JSON，也不写回媒体目录。每项缓存带来源长度、UTC 修改时间和签名；容量超限时只淘汰本机缓存。设置中的“清理缓存”只枚举并删除该缓存目录内的 payload、元数据和临时文件，不会删除音乐、LRC、歌单、收藏或 NAS 文件。

缓存枚举会跳过 symlink、junction 和其他 reparse point；读、写、替换或删除前还会再次检查规范化路径是否位于缓存根目录。即使缓存目录中被放入指向外部位置的 junction，“清理缓存”也只会处理真实缓存文件，不会穿过链接删除目标目录内容。

### 大小上限与恢复行为

| 输入 | 上限 | 超限行为 |
| --- | ---: | --- |
| 状态 JSON | 文件 256 MiB；单字符串 UTF-8 256 KiB | 不进入模型；主文件超限时继续尝试 `backup`、`previous`，且不再复制一份超大 invalid 文件 |
| LRC 歌词 | 8 MiB | 忽略该歌词文件，播放器继续使用无歌词或最后一份有效本机缓存 |
| 本机歌词缓存 | 16 MiB | 拒绝读取/写入该缓存条目 |
| 封面、背景图与封面缓存 | 32 MiB | 在完整读入和解码前拒绝；解码边界最高 1600×1600 |
| 网易云播放历史 | 64 MiB | 导入失败并明确返回超限错误，不修改现有播放次数 |
| 网易云歌单/歌曲详情响应 | 32 MiB / 8 MiB | 停止缓冲和解析；重试后仍超限则导入失败，不替换旧歌单 |

状态写入也受 256 MiB 上限约束。序列化临时文件超限时，本次保存失败并删除临时文件，原主文件与恢复点保持不变。

## 一次保存如何完成

1. 获取进程内写锁。
2. 获取 `library-v2.write.lock` 的独占文件锁。
3. 对现有主文件和备份检查文件戳；首次遇到或文件被外部改动时才完整反序列化校验。
4. 把强类型 `AppState` 序列化到同目录唯一临时文件，并刷新文件缓冲到磁盘。
5. 把已确认有效的原 `backup` 轮换为 `previous`。
6. 把已确认有效的原主文件轮换为 `backup`；复制完成后核对字节长度。
7. 原子替换主文件，并记录新文件戳供后续保存复用。
8. 如果此前没有有效恢复点，再从新主文件建立初始 `backup`。

任何可恢复的 I/O、权限或 JSON 异常都会写入日志并重新抛给调用方。界面不会再把失败保存当作成功保存。

## 为什么备份不能与主文件相同

如果程序错误地准备保存一个空曲库，而保存后再把新主文件复制成唯一备份，那么主文件和备份会同时变空，无法抵抗逻辑性数据丢失。1.6.3 及之后版本的 `backup` 始终保留替换前的上一代，因此即使新状态语义错误，仍有旧状态可恢复。

首次创建状态时没有“上一代”，所以初始 `backup` 可能与主文件相同；从第二次保存开始，两者承担不同代次。

## 增量扫描规则

每首歌曲保存：

- 文件大小 `FileSize`
- UTC 修改时间 `LastWriteTimeUtcTicks`

普通扫描时：

- 路径、大小和修改时间均未变化：复制缓存元数据和用户状态，不打开 TagLib。
- 旧状态没有文件戳：先信任已有元数据并补齐当前文件戳，避免升级后立刻全盘重读。
- 新文件或文件戳变化：重新读取标签、时长、封面和歌词信息。
- “重新识别社团”：强制刷新可访问文件的元数据。

取消扫描会丢弃本次结果，不替换当前 `_state.Tracks`，也不会调用状态保存。TagLib 的单文件读取是同步 I/O，已经进入的那次读取无法被令牌从内部打断；界面会在它返回后停止后续工作。

## 离线磁盘和失败目录

- 配置根目录不存在时，该根目录下的旧索引被保护。
- 可访问根目录中的某个子目录枚举失败时，该子目录被加入保护位置。
- 扫描遇到目录或媒体文件的 reparse point 时不会跟随；该位置按不可安全扫描处理，既避免目录循环，也避免越过所选曲库根目录。
- 可访问目录中确认不存在的文件仍会按正常删除处理。
- 配置根目录之外的旧条目不会无条件保留。
- 播放列表清理只有在扫描结果可信时才允许进行。

因此，“硬盘暂时没插”与“文件已经从在线硬盘删除”是两个不同状态。

## 单实例保护

应用使用固定的当前用户会话命名 Mutex。第一个实例持有锁；后续实例在创建 LibVLC、热键、托盘和音频资源前停止。

文件写锁只能保证 JSON 不被同时写坏，不能解决两个实例各自持有不同内存状态后“最后保存者覆盖前者”的问题。单实例保护用于消除这个语义覆盖风险。

## 手动恢复

在操作前先彻底退出 OfflineMusicLibrary，并复制整个状态目录到另一个位置。

推荐顺序：

1. 保留当前 `library-v2.json`，不要直接删除。
2. 检查 `logs\player.log` 中最近的 `STATE` 和 `LibraryScan` 记录。
3. 如果主文件损坏，正常启动会自动尝试 `backup`，再尝试 `previous`。
4. 如果必须手动回退，把当前主文件改名保存，再复制有效备份为 `library-v2.json`。
5. 启动后先确认歌曲数量、歌单数量和收藏，再执行新扫描。

不要把完整状态文件公开上传。它可能包含用户名、盘符、私人目录结构、歌单名称和播放历史。

## 验证边界

回归测试验证增量复用、修改刷新、reparse point 跳过、离线根目录保留、取消不原地修改、探测并发上限、单实例、上一代备份、第二级恢复、超大主状态回退、保存失败传播、缓存根目录边界、超大歌词/封面/历史/HTTP 响应拒绝、并发完整性、遗留临时文件清理，以及 6,000 首大状态的保存耗时与内存分配门槛。它们不启动播放器界面，也不能证明每一种硬盘固件、杀毒软件、显卡驱动或突然断电时序下都绝对不会失败；多代恢复用于降低而不是宣称消灭这些风险。
